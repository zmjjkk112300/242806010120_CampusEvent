# 01 初始需求分析

## 1.1 项目定位

CampusEvent 面向校园场景：管理员发布活动，学生浏览并报名；报名分“直接报名”与“管理员审核”两类；报名与审核结果通过站内消息通知。
本版本为初始验收版本 **baseline-v1**，只实现指导书 3.2 节与附录 B 规定的初始需求，不实现任何变更功能。

## 1.2 角色与权限

| 角色 | 使用方式 | 权限 |
|---|---|---|
| 学生 Student | 固定演示账号登录（S001—S003） | 浏览活动、按名称筛选、查看详情、报名、取消报名、查看我的报名、查看站内消息 |
| 管理员 Admin | 固定账号 admin / admin123 | 创建、编辑、删除活动；查看待审核报名；批准或拒绝；查看活动统计 |

## 1.3 领域数据（对应附录 B.1）

| 对象 | 字段 | 约束与实现要点 |
|---|---|---|
| Student | student_id、name | student_id 主键唯一；演示账号预置 3 个 |
| Activity | activity_id、title、category、start_at、location、capacity、policy_type | capacity 为 1—1000 正整数；policy_type ∈ {direct, approval}；start_at 必须可解析为合法时间 |
| Registration | registration_id、activity_id、student_id、status、created_at、updated_at | status ∈ {待审核, 已通过, 已拒绝, 已取消}；同一学生对同一活动最多一条“待审核/已通过”记录 |
| Message | message_id、student_id、activity_id、content、created_at、is_read | 增加 `event_key` 唯一约束作为幂等键，保证“同一事件只通知一次” |

## 1.4 业务规则（对应附录 B.2，逐条落地）

| 编号 | 规则 | 落地位置 |
|---|---|---|
| R1 | 直接报名：名额充足且符合基本条件时直接“已通过”并通知 | `DirectRegistrationPolicy.decide()` + `RegistrationService.register()` |
| R2 | 审核型：提交后“待审核”，管理员批准/拒绝，批准时再查名额 | `ApprovalRegistrationPolicy.decide()` + `RegistrationService.approve()` |
| R3 | 名额按“已通过”计算，待审核不占名额；满员不得再批准 | `RegistrationService.approved_count()/stats()`，`approve()` 内复查 |
| R4 | 同一活动不得同时存在两条“待审核/已通过”有效报名；已取消/已拒绝保留历史，可再次申请 | `RegistrationRepository.active_of()` + `RegistrationService.register()` |
| R5 | 学生可取消自己的“待审核/已通过”报名；活动开始后不得新增报名 | `RegistrationService.cancel()/register()` 的 `start_at` 校验 |
| R6 | 通知失败应留痕，不得让已合法提交的报名无声消失 | 事件在事务提交后发布；观察者独立会话写入，失败由 `DomainEventBus` 记录 `failures` 并写日志 |
| R7 | 数据必须持久化；删除有报名的活动需明确策略 | 选择“拒绝删除并提示”，`ActivityRepository.delete()` 抛 `HasRegistrations` |

## 1.6 非功能需求

- 单机 Web 应用，Flask + SQLite，`python run.py` 即可启动，无需外部服务。
- 页面全中文，操作失败给出明确中文提示，不出现 500 或静默失败。
- 关键业务规则有自动化测试覆盖，`pytest` 可重复运行。
- 提供 `requirements.txt`、`README.md`、`AI_DEV_LOG.md`。
- 部署到云服务器，README 给出启动命令与访问地址。

## 1.7 范围外（明确不做）

用户注册与密码体系、多角色细粒度权限、邮件/短信/微信通知、消息队列、活动签到、支付、移动端 App、活动推荐算法。
变更单（CR）发布前不得提前实现任何变更功能，本仓库亦未预留半成品代码。
