# 10 CR-02 邮件通知：影响分析与设计（v2）

> 变更单：CR-02　版本：baseline-v1 → change-v2

## 10.1 变更要求（原文要点）

1. 报名通过（直接报名、审核通过）与审核拒绝两类事件，在**保留站内通知**的同时新增邮件通知；
2. 邮件由 `MockEmailSender` 模拟发送，须记录**收件人、主题、内容、状态、时间**；
3. 邮件故障必须**记录错误**，但**不得回滚报名**；
4. 同一业务事件**不得重复发送**；
5. 期望通过观察者/事件结构实现，**不把邮件代码写进 `RegistrationService`**。

验收用例：CR2-01 直接报名通过 → 站内 + 邮件均有记录；CR2-02 审核批准/拒绝 → 两渠道对应结果；CR2-03 发送失败 → 报名状态正确且错误有日志；CR2-04 重复提交 → 不重复生成；CR2-05 重跑 C1—C10 通过。

## 10.2 影响分析（实施前完成）

| 层 | 构件 | 是否改动 | 影响与理由 |
|---|---|---|---|
| 事件 | `events.py` 的 `RegistrationEvent` / `DomainEventBus` | 基本不改 | 已有 `event_key()` 与失败留痕 `failures`，天然满足“同一事件一次”和“失败不吞掉”的基础设施；仅补一个 `unsubscribe()` 便于测试与热插拔 |
| 观察者 | `notifications.py` | 改 | 新增 `EmailNotificationObserver`，与站内观察者**并列**订阅同一条事件；`InAppNotificationObserver` 一行未改 |
| 端口 | 新增 `app/mailer.py` | 新增 | `EmailSender` 抽象 + `MockEmailSender`（可注入失败次数）；发送方式可替换为真实 SMTP，观察者不感知 |
| 数据 | `models.py` | 改 | 新增 `EmailRecord`（收件人、主题、内容、状态、错误、时间、`event_key`），满足“必须记录”与可审计 |
| 装配 | `extensions.py` / `__init__.py` | 改 | 事件总线同时订阅两个观察者；`CAMPUS_EVENT_EMAIL_FAIL_TIMES` 注入故障次数，便于演示与测试 |
| 服务 | `RegistrationService` | **不改** | 事件仍在事务提交后发布，邮件失败发生在订阅侧，报名事务已落库 |
| 页面 | 新增 `/admin/emails` | 新增 | 管理员可查看邮件发送记录与失败原因（证据可视化） |
| 数据迁移 | 既有库 | 改 | 新增 `email_records` 表由 `create_all` 建；`students.email` 由 `ensure_schema()` 补列 |
| 测试 | 新增 CR2-01—05 | 改 | 原 23 条断言不变 |

**风险点与对策**

| 风险 | 说明 | 对策 |
|---|---|---|
| 邮件故障连带报名失败 | 若在 `RegistrationService` 内同步发信并抛异常，报名会被回滚 | 发信放在后置的独立观察者 + 独立会话；捕获 `EmailSendFailed` 后先落失败记录，再抛出交由总线记 `failures`，报名已提交不受影响 |
| 重复邮件 | 重试、重复点击、事件重投都可能触发 | 双重保险：`(recipient, event_key)` 唯一约束 + 发送前查重；`event_key` 由报名单号与事件名构成，同一状态天然唯一 |
| 观察者互相影响 | 站内通知成功、邮件失败时，不能让前者被连坐 | 总线逐个调用并各自 try，失败只进 `failures` 列表；两个观察者使用各自会话 |
| 学生没有邮箱 | 演示数据可能缺字段 | 回退默认地址 `{student_id}@campus.example.edu`，保证链路不中断，并在文档中说明 |
| 邮件内容与站内涵义不一致 | 两渠道文案各写一套易漂移 | 邮件只订阅 `EMAIL_EVENTS = (approved, rejected)`，主题/正文与站内模板语义对齐，拒绝原因均指向“未通过审核” |

## 10.3 设计决策

**决策 1：并列观察者，而不是改造站内观察者。**

`InAppNotificationObserver` 已承担“写站内消息 + 幂等”职责。邮件是**独立渠道**，合并会让单个类承担两种失败语义（站内失败要不要发邮件？邮件失败要不要重发站内？）。拆分后：

```
DomainEventBus.publish(event)
  ├─ InAppNotificationObserver.handle(event)   # 写 Message
  └─ EmailNotificationObserver.handle(event)   # 查重 → send → 写 EmailRecord
```

**决策 2：端口—实现分离（`EmailSender` 抽象 + `MockEmailSender`）。**

课程要求“模拟发送”，但真实项目会换成 SMTP/第三方服务。把发送动作抽成接口，观察者只依赖 `send(recipient, subject, body)`；`MockEmailSender(fail_times=1)` 前 N 次抛 `EmailSendFailed`，用于构造 CR2-03 的故障场景，也便于演示时手动触发。

**决策 3：先落记录、再抛异常。**

顺序是「捕获失败 → 写 `EmailRecord(status=发送失败, error=…)` → commit → raise」。这样无论上层如何处理，失败证据一定在库里；异常继续冒泡只是为了让总线把这次失败计入 `failures` 并打日志，符合“错误有日志、报名不回滚”。

**决策 4：幂等键复用领域事件的 `event_key`。**

`event_key = f"{registration_id}:{event_name}"`。邮件表对 `(recipient, event_key)` 建唯一约束，查重先于发送，因此重复投递既不会多发信，也不会多写记录。

## 10.4 实施要点（代码落点）

| 文件 | 改动 |
|---|---|
| `app/constants.py` | `EMAIL_EVENTS = (EVENT_APPROVED, EVENT_REJECTED)`；`EmailStatus`（已发送 / 发送失败） |
| `app/mailer.py` | `EmailSender`（ABC）、`MockEmailSender(fail_times, logger)`，成功返回发送时间并记入 `sent` |
| `app/models.py` | `EmailRecord`（`email_id, student_id, activity_id, recipient, subject, body, status, error, event_key, created_at`，唯一约束 `(recipient, event_key)`）；`Student.email` |

| `app/extensions.py` | `init_event_bus()` 一并订阅站内与邮件观察者，暴露 `email_sender()` |

| `app/routes.py` / `repositories.py` | `EmailRepository.list_all()` + `/admin/emails` 页面 |

| `tests/test_change_v2.py` | CR2-01—05 |

**明确未改**：`services.py`（事件发布时机与顺序仍是“commit 之后 publish”）。
