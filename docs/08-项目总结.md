# 08 项目总结（baseline-v1）

> 本文件是 Word 实验报告（`CampusEvent_实验二实验报告.docx`）的 Markdown 版本，便于仓库内直接阅读与提交。
> 章节与附录 D.1 的统一目录一致。

## 一、实验目标与需求范围

实验二的要求是：学生先做设计，再指导 AI 实现，随后面对教师发布的变更评估影响并修改系统，最后用可测指标评价设计价值。
本项目 CampusEvent 完成初始版本的**设计、实现、测试、部署**四件事，并封存为 Git 标签 `baseline-v1`，为变更阶段提供对照基线。

范围限定为：管理员发布活动（8 项功能中的 P2-F01）、学生浏览报名（F02—F04）、审批（F05—F06）、站内通知（F07）、统计（F08）。
明确不做：注册与权限体系、邮件短信通知、消息队列、签到支付、移动端。变更单发布前不实现、也不预留任何变更功能。

## 二、实现方案

### 2.1 环境

Windows 11 + Python 3.13.18（venv）、Flask 3.1.3、SQLAlchemy 2.1.9、SQLite、pytest 8.4.2、gunicorn 23.0.0。

### 2.2 分层

```
表现层（student / admin 蓝图）→ 应用服务层 RegistrationService
        → 仓储层（4 个 Repository）→ 领域模型（4 张表）
        → 策略层 PolicyRegistry → RegistrationPolicy
        → 事件层 DomainEventBus → InAppNotificationObserver
```

依赖单向向下：路由不写 SQL，服务不做页面渲染，领域模型不依赖上层。类图与职责详见 `03-类图与职责.md`。

### 2.3 关键设计

| 设计点 | 结论 | 理由 |
|---|---|---|
| 报名规则 | 策略模式：`decide()` 返回初始状态与事件 | 新增规则 = 新增类 + 注册，服务零改动 |
| 名额检查 | 算法属公共不变量（服务层），占用时点由策略声明 `occupies_capacity_on_submit` | 避免容量逻辑复制进每个策略，又保留规则差异 |
| 通知解耦 | 领域事件 + 观察者，事务提交后发布 | 通知渠道可扩展，通知失败不回滚报名 |
| 幂等 | `Message(event_key)` 唯一约束 + 写前查重 | 重复投递只留一条，重启后仍有效 |
| 状态流转 | 只在 `RegistrationService` 四个方法内发生 | 杜绝“漏校验导致已拒绝记录被再次批准” |
| 删除活动 | 有报名则拒绝删除 | 级联删除会丢失学生报名历史，软删除需全查询加过滤 |

### 2.4 数据模型

`students`、`activities`、`registrations`（状态：待审核/已通过/已拒绝/已取消）、`messages`（含幂等键 `event_key`）。

## 三、实施过程

1. **设计先行**：需求分析 → 用例说明 → 类图 → 报名与审批时序图 → 设计原则说明；由同组同学评审并签名后进入编码。
2. **AI 协作**：由 AI 按已评审设计产出代码与测试，人工逐项核对设计边界，拒绝偏离设计的建议（详见 `AI_DEV_LOG.md` 九条记录）。
3. **版本管理**：`git commit` 后打标签 `baseline-v1`；变更阶段将在该标签上开分支，产出 `change-v2`。
4. **部署**：云主机建 venv、装依赖、跑测试、gunicorn 双 worker 后台运行，服务器本机登录页返回 200，服务器上 pytest 23 passed。
   该云主机安全组未对公网放行 8000 端口（实测 80/443/8000/8080 均不可达），因此无法给出公网地址；仓库提供 `deploy/deploy.sh`
   与 systemd 单元，迁移到具备公网端口的服务器时一条命令即可部署。

## 四、测试结果

`pytest -q` → **23 passed**（约 1.5 秒）。C1—C10 逐条通过，另有 13 条边界与页面流程用例：

| 用例 | 场景 | 结论 |
|---|---|---|
| C1—C10 | 创建、报名、重复、满员、待审核、批准、拒绝、批准超员、取消、重启 | 全部通过 |
| E1 | 取消后再次申请 | 旧记录保留，新记录待审核 |
| E2 | 活动已开始后报名 | 拒绝 |
| E3 | 删除有报名的活动 | 拒绝并提示 |
| E4 | 通知服务不可用 | 报名仍成功，失败留痕 |
| E5 | 同一事件重复投递 | 仅一条通知 |
| E6 | 取消他人报名 | 拒绝 |
| E7/E8/E9 | 非法策略、未知学生、非法状态迁移 | 均拒绝且不产生脏数据 |
| W1—W4 | 登录报名、审批、空名称表单、未登录拦截 | 页面流程符合预期 |

缺陷记录：会话工厂返回值错误（6 条用例失败，一处修复）、事件发布早于提交（幽灵通知）、内存去重失效（改数据库唯一约束）。

## 五、结果分析

基线指标：15 个 Python 文件 / 1365 行、2 个抽象点、2 个策略实现、3 个核心业务类、23 条用例、需求覆盖 8/8、回归失败 0。

预期变更半径：新增报名规则 → 新增策略类，核心类 0 改动；新增通知渠道 → 新增观察者，报名流程 0 改动；
修改名额口径 → 策略声明 + 统计口径，核心服务 1 处小改。

模式成本（如实）：代码量增加约四成；通知与报名弱一致，需日志与补偿意识；两种规则下抽象存在“为模式而模式”的风险。
因此评价标准不是“用了模式”，而是变更时的新增类数、修改核心类数与回归失败数。

## 六、问题与反思

1. **AI 的方案会破坏设计**：通知写在同一事务并抛异常，演示正常但违反“通知失败不得使报名无声消失”。经验是用需求条文与用例校验 AI 输出，而非“能跑通”。
2. **模式不能替代底层理解**：会话工厂与会话实例混淆导致 6 条用例失败，AI 建议加类型判断掩盖症状；靠异常栈定位根因后一处修复。设计模式解决耦合，不替代框架与事务机制的基本功。
3. **尚存局限**：固定演示账号、SQLite 未做并发压测、通知失败只留痕不重试。
