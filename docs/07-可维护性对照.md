# 07 可维护性对照（baseline-v1 → change-v2）

对照原则：不用“是否使用了设计模式”作为结论，只看可测量的修改成本。

## 7.1 指标定义

| 指标 | 定义 |
|---|---|
| 新增类数 | 变更引入的新类（含抽象类、值对象、策略实现、观察者） |
| 修改的核心业务类数 | `RegistrationService`、`ActivityRepository`、`RegistrationRepository` 等初始核心类中被改动的个数 |
| 回归失败数 | 变更后重跑 C1—C10 与边界用例的失败条数 |
| AI 交互轮次 | 变更阶段向 AI 下达的有效指令轮次（不含闲聊与重复确认） |
| 修改总时长 | 从影响分析到回归通过的实际耗时（人时） |
| 代码基线 | 生产代码 Python 文件数 / 行数 |

## 7.2 baseline-v1 实测基线

| 指标 | baseline-v1 数值 | 备注 |
|---|---|---|
| Python 文件数 | 15（app 11 + tests 2 + 其他 2） | `run.py`、`tests/conftest.py` 计入 |
| 生产代码行数 | 1365 行（含测试 352 行） | 其中 `app/` 约 1013 行 |
| 模板文件 | 10 个 Jinja2 页面 | 中文界面 |
| 抽象点 | `RegistrationPolicy`（1 个接口）、`DomainEventBus`（1 个事件总线） | 策略实现 2 个 |
| 核心业务类 | 3 个：`RegistrationService`、`RegistrationRepository`、`ActivityRepository` | 变更时重点观察其改动 |
| 自动化用例 | 23 条（C1—C10 + 13 条边界/页面） | 全部通过 |
| 需求覆盖 | P2-F01—P2-F08 全通过 | 见 `01-需求分析.md` 映射表 |
| Git 标签 | `baseline-v1` | 初始验收版本封存 |

## 7.3 变更对照表（CR-01 / CR-02 实施后实测）

| 指标 | baseline-v1 | change-v2 | 差值 | 说明 |
|---|---|---|---|---|
| 新增类数 | 8（含 2 个策略实现、2 个仓储、3 个实体、1 个事件） | 15 | +7 | 新增 `RegistrationRule`、`GradeRangeRule`、`CompositePolicy`、`GradeLimitedDirectPolicy`、`EmailSender`、`MockEmailSender`、`EmailNotificationObserver`；另加 `EmailRecord` 实体 |
| 修改的核心业务类数 | — | **0** | 0 | `app/services.py`、`app/repositories.py` 的既有类方法未改；仅新增 `EmailRepository` |
| 新增测试数 | 23 | 36 | +13 | CR1-01—05、页面 1 条、CR2-01—05、迁移 1 条、演示补齐 1 条 |
| 回归失败数 | 0（基线） | **0** | 0 | 36 passed，含 C1—C10 原断言 |
| AI 交互轮次 | 9（设计+实现+修复） | 6（影响分析 → 编码 → 测试修复 → 文档） | — | 见 `AI_DEV_LOG.md` |
| 修改总时长 | 约 2 天（设计与实现） | 约 3 小时（含文档与部署） | — | 人时，单人口述需求 + AI 协作 |
| 生产代码规模 | 15 个 .py / 1365 行 | 21 个 .py / 2661 行（app 1341 行） | +6 文件 | 增量主要在测试与脚本 |
| Git 标签 | `baseline-v1` | `change-v2` | — | 两版均可追溯 |

**结论**：两类变更都落在“新增类”上，核心服务零改动，与 7.4 的预期完全一致；偏差项只有测试与文档代码量增加（这部分不计入生产复杂度）。

## 7.4 预期与判断标准（变更前事先声明）

依据初始设计，预期以下三类变更的修改半径：

| 变更类型 | 预期修改点 | 预期新增类 | 核心类改动 |
|---|---|---|---|
| 新增一种报名规则（如抽签） | 新增 1 个 `Policy` 实现 + 注册表一行 | 1—2 | 0（若抽签需要随机名额预留，可能需扩展 `RegistrationContext`，则服务有 1 处小改） |
| 新增通知渠道（如邮件） | 新增 1 个观察者 + 订阅一行 | 1 | 0 |
| 修改名额口径（如待审核也占名额） | 修改 `occupies_capacity_on_submit` 与统计口径 | 0 | 1（`RegistrationService`） |

若实际变更结果与预期偏差较大，需在报告中如实分析原因（例如“策略抽象粒度不够，导致服务仍需改类型判断”）。
