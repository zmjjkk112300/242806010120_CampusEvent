# 09 CR-01 年级限定报名：影响分析与设计（v2）

> 变更单：CR-01　版本：baseline-v1 → change-v2　提交前置要求：先影响分析、后实施

## 9.1 变更要求（原文要点）

1. `Activity` 支持「年级限定直接报名」这一新的报名方式；
2. `Student` 新增 `grade`（取值 1—4，分别对应大一—大四）；
3. 限定活动**只有 2、3 年级学生可以报名**，其他年级报名时给出**明确原因**；
4. 年级限定仍须遵守名额、开始时间、重复报名等公共约束；
5. 原有 `direct` / `approval` 行为**不得改变**。

验收用例：CR1-01 大二通过、CR1-02 大三通过、CR1-03 大一拒绝且有原因、CR1-04 大四拒绝且有原因、CR1-05 重跑 C1—C10 全通过。

## 9.2 影响分析（实施前完成）

| 层 | 构件 | 是否改动 | 影响与理由 |
|---|---|---|---|
| 领域模型 | `Student` | 改 | 新增 `grade` 列（默认 1）；无年级无法判定资格，属于不可回避的数据模型变更 |
| 领域模型 | `Activity` | 改 | 新增 `min_grade` / `max_grade`（可空，闭区间）；用区间而非硬编码“2、3”，避免把业务规则冻结在代码里 |
| 枚举 | `PolicyType` | 改 | 新增 `grade_direct`，与 `direct` 并存；**不修改**已有两种枚举取值，保证旧数据与旧行为不变 |
| 策略 | `policies.py` | 改 | 新增年级限定策略与规则链；`DirectRegistrationPolicy` / `ApprovalRegistrationPolicy` 一行未改 |
| 服务 | `RegistrationService` | **不改** | 核心不变量的校验顺序、状态流转、事件发布位置全部保持原样，年级限制在策略 `decide()` 内完成 |
| 异常 | `errors.py` | 改 | 新增 `GradeNotAllowed`（`DomainError` 子类），复用现有路由的 DomainError → flash 提示链路 |
| 仓储 | `repositories.py` | 不改 | 年级条件读的是实体字段，无需新增查询 |
| 路由/模板 | 活动表单、活动详情 | 改 | 表单需录入年级区间；详情页需展示「年级限定」；报名按钮与提示复用原有分支 |
| 数据 | 既有 SQLite 库 | 改 | 旧库无新列，需轻量迁移；已有活动 `min_grade/max_grade` 置 NULL，语义为“无年级限制”，行为不变 |
| 测试 | `conftest` / 新增用例 | 改 | 学生需带年级；新增 CR1-01—05；原 23 条不改断言 |

**风险点与对策**

| 风险 | 说明 | 对策 |
|---|---|---|
| 破坏既有直接报名 | 若在 `RegistrationService` 里加 `if policy_type == grade_direct` 分支，会污染核心服务并易漏判 | 采用策略 + 规则链组合，服务零改动；`direct` 仍走原策略实例 |
| 年级规则与名额/时间校验顺序错乱 | 若先校验年级再校验名额，提示语义会自相矛盾 | 复用服务原有顺序：先公共不变量（时间、重复、名额），再策略决定；年级仅在策略内判定 |
| 旧库升级失败 | 直接 `create_all` 不会给已有表加列 | `ensure_schema()` 用 `PRAGMA table_info` 探测后 `ALTER TABLE` 补列，幂等可重入 |
| 提示不明确 | 只说“不能报名”不满足 CR 要求 | 异常消息含允许区间与当前年级，如“仅面向大二—大三学生报名，你当前是大一” |

## 9.3 设计决策

**决策 1：规则（Rule）+ 组合策略（Composite），而不是给服务加分支。**

```
RegistrationRule（只回答“是否放行”，不决定状态）
  └── GradeRangeRule          读 activity.min_grade / max_grade，越界抛 GradeNotAllowed
CompositePolicy(rules, inner) 先跑规则，再委托内层策略产出 RegistrationDecision
  └── GradeLimitedDirectPolicy = CompositePolicy([GradeRangeRule], DirectRegistrationPolicy)
```

理由：
- **职责单一**：规则只判“能不能”，策略只判“报完是什么状态”，两者不互相污染；
- **可叠加**：将来若要“限定专业”“限定学院”，加一条 Rule 即可，不必再改服务或新建策略；
- **零侵入**：`RegistrationService.decide()` 调用的仍是 `policy.decide(context)`，签名不变；
- **可测**：`GradeRangeRule` 可脱离 Flask 单独测边界（2/3 通过，1/4 拒绝，NULL 视为不限）。

**决策 2：年级用区间字段而非枚举集合。**

`min_grade/max_grade` 表达闭区间，NULL 表示不限制。相比“允许年级列表”，区间更贴合“大二大三专属”这类表述，表单是两个下拉框，且能自然覆盖“大一至大三”等未来需求。

**决策 3：非法输入在入口处快速失败。**

表单解析对 `grade_direct` 取值做 1—4 校验并要求 `min_grade <= max_grade`，不合法直接拒绝提交；其余策略一律把两个字段置 NULL，避免出现“direct 活动却带年级限制”的脏数据。

## 9.4 实施要点（代码落点）

| 文件 | 改动 |
|---|---|
| `app/constants.py` | `PolicyType.GRADE_DIRECT = "grade_direct"`（标签「年级限定直接报名」）；`GRADE_TEXT` 1—4 中文映射 |
| `app/models.py` | `Student.grade`（Integer, default 1）、`Student.grade_label`；`Activity.min_grade` / `max_grade`（nullable） |
| `app/policies.py` | `RegistrationRule`、`GradeRangeRule`、`CompositePolicy`、`GradeLimitedDirectPolicy`，并注册进 `PolicyRegistry` |
| `app/errors.py` | `GradeNotAllowed` |
| `app/routes.py` | `_parse_activity_form` 解析并校验年级区间；`inject_globals` 补 `grade_direct` 标签 |
| `app/templates/admin_activity_form.html` | 新增「年级区间」两个下拉（`.inline` 容器） |
| `app/templates/activity_detail.html` | `grade_direct` 时显示「年级限定：大二—大三」 |
| `app/extensions.py` | `ensure_schema()` 补列并回填演示学生年级 |
| `tests/conftest.py` | 演示学生带 `grade`/`email`；`make_activity` 支持 `min_grade`/`max_grade` |
| `tests/test_change_v2.py` | CR1-01—05 + 页面流程 1 条 |

**明确未改**：`services.py`、`repositories.py`、`events.py` 的事件定义、`notifications.py` 的站内观察者。
