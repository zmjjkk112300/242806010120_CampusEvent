# 05 设计模式决策报告

本报告只说明**本人做出的设计决策**及其理由、代价和验证方式。AI 负责按决策实现代码；凡是与本报告冲突的 AI 建议均被拒绝或改写（见 `AI_DEV_LOG.md`）。

## 决策一：用策略模式承载“报名规则”，而不是在服务里写分支

**问题**：报名规则会随活动类型变化，初始有两种（直接报名、审核报名），后续极可能增加（如限额抽签、班级定向、候补队列）。

**备选方案对比**

| 方案 | 做法 | 后果 |
|---|---|---|
| A. 服务内 if/elif | `if activity.policy_type == 'direct': ... elif ...` | 每加一种规则就改核心服务；分支与状态赋值、通知逻辑耦合，回归测试范围随类型数线性增长 |
| B. 配置表驱动 | 在数据库里配置“是否需要审核”等布尔字段 | 只能表达“是/否”，无法表达抽签、候补这类需要独立算法的规则 |
| C. 策略模式（采用） | 抽象 `RegistrationPolicy`，两种实现 + 注册表 | 新增规则只新增一个类并注册；服务代码零改动；策略可独立单测 |

**落地方式**

```python
class RegistrationPolicy(ABC):
    policy_type: PolicyType
    occupies_capacity_on_submit: bool = False
    @abstractmethod
    def decide(self, context: RegistrationContext) -> RegistrationDecision: ...
```

- `DirectRegistrationPolicy` → 已通过 + `registration.approved`
- `ApprovalRegistrationPolicy` → 待审核 + `registration.submitted`
- `PolicyRegistry` 按 `policy_type` 取实现，**服务层不存在报名类型判断**（可 `grep` 验证：`services.py` 中无 `policy_type ==`）。

**代价**：多出 1 个抽象类、2 个实现、1 个注册表、2 个值对象，约 70 行代码；对只做两种规则的课程项目而言，结构确实比“一个 if/else”更复杂。收益在于变更时的修改半径与测试范围可控。

## 决策二：名额检查是公共不变量，但“检查时点”由策略声明

指导书要求说明“名额检查属于公共规则还是策略责任”。结论是**两者都要，但分工明确**：

- 名额是活动的属性，超员是任何规则都不能违反的硬约束 → 校验算法（`approved_count < capacity`）属于公共规则，放在 `RegistrationService`，避免每个策略各写一份。
- 但“什么时候占用名额”随规则不同：直接报名提交即占用；审核型要等批准才占用（附录 B.2 规则 3 明确“待审核不占名额”）。因此策略只暴露一个布尔语义 `occupies_capacity_on_submit`，服务据此决定在提交阶段还是批准阶段校验。

这样既不把容量算法复制进策略，也不让服务去猜每种规则的行为。验证：C4（提交阶段超员）、C8（批准阶段超员）。

## 决策三：用观察者（事件总线）解耦报名业务与通知

**问题**：报名成功后要写站内消息；未来可能加邮件、短信、企业微信。若直接在 `register()` 里写消息表，通知渠道数量会让报名方法不断膨胀，且通知异常会污染报名结果。

**方案**：定义 `RegistrationEvent` + `DomainEventBus`，服务只在事务提交后 `publish`；`InAppNotificationObserver` 订阅全部报名事件并写 `Message`。

**两个必须回答的问题**

1. **通知失败是否影响报名事务？** 不影响。事件在 `commit()` 之后发布，观察者使用**独立会话**写入；失败由总线捕获、记录到 `failures` 并打日志。报名记录已合法提交，不会无声消失（对应 B.2 规则 6 与测试 `test_extra_notification_failure_does_not_rollback_registration`）。
2. **如何避免重复通知？** `Message` 表加 `(student_id, event_key)` 唯一约束，`event_key = 事件名:报名ID`；观察者写前查重，重复投递直接跳过（测试 `test_extra_duplicate_event_produces_single_message`）。相比在内存里记录已处理事件，这个方案重启后依然有效。

**代价**：消息最终一致——通知与报名不在同一事务，极端情况下可能出现“报名成功但通知缺失”，因此必须保留失败日志与补偿意识；调用链变长，排查问题时需要看事件总线日志。

## 决策四：状态流转只有一个入口

四种状态、七条合法迁移如果散落在路由、模板、仓储中，必然出现“某处漏校验”的缺陷（例如已拒绝记录被再次批准）。
本项目所有状态变更只在 `RegistrationService` 的四个方法里发生，路由只调用方法、不直接改 `status`。非法迁移统一抛 `InvalidStatusTransition`，由路由转成中文提示。

## 决策五：删除有报名的活动选择“拒绝删除”

三种可选方案：级联删除、软删除、拒绝删除。

| 方案 | 风险 |
|---|---|
| 级联删除 | 静默删除学生的报名历史，数据不可追溯，统计口径突变 |
| 软删除 | 需在所有查询、统计、唯一性校验上加过滤条件，遗漏一处就出现“幽灵活动” |
| 拒绝删除（采用） | 管理员会收到明确提示，操作成本稍高，但数据最安全 |

课程项目数据量小、以正确性为先，故选第三种；`ActivityRepository.delete()` 内统计报名记录数后决定是否抛 `HasRegistrations`。

## 决策六：仓储层承担 SQL，服务层只依赖语义方法

`RegistrationRepository.count_by_status()`、`active_of()` 等方法把 SQL 细节隔离；服务层只表达“统计已通过人数”“查有效报名”。
好处：单测可以直接针对服务与内存 SQLite 运行，不依赖 Flask 请求上下文；将来换 MySQL 只改连接串与少量方言。

## SOLID 对照

| 原则 | 本项目的体现 | 反例（若违反） |
|---|---|---|
| 单一职责 | 路由只管 HTTP，服务只管规则，策略只管决策，观察者只管通知 | 一个 `register()` 里既建记录又发短信又写统计 |
| 开闭原则 | 新增报名规则 = 新增策略类 + 注册，服务不改 | 服务内 if/elif 增长 |
| 依赖倒置 | 服务依赖策略抽象、事件总线抽象、仓储语义 | 服务直接 `import requests` 发通知 |
| 接口隔离 | `RegistrationPolicy` 只有一个 `decide()` | 策略接口塞入数据库操作 |
| 里氏替换 | 两个策略实现可互换，服务行为只由返回值差异决定 | 策略内部偷偷写库 |

## 未来扩展点（为变更版预留的判断，不含实现）

- 新报名规则：新增 `XxxPolicy` 并 `registry.register()`。
- 新通知渠道：新增观察者并 `bus.subscribe_all()`，报名服务不动。
- 候补/排队：需要一个新的“名额分配者”角色，但仍由服务在占用时点调用。
- 活动删除策略调整：改 `ActivityRepository.delete()` 一处。

## 成本如实说明

1. 代码量比“单文件 if/else”多约 40%，初次阅读需要理解注册表与事件总线。
2. 通知不再与报名强一致，需要日志与补偿机制。
3. 策略抽象目前只有两个实现，存在“为模式而模式”的嫌疑；判断标准不是“用了模式”，而是变更时**新增类数、修改的核心类数、回归失败数**三项指标（见 `07-可维护性对照.md`）。

## 决策七（v2 / CR-01）：年级限制做成“规则 + 组合策略”，而不是服务里的 if

- **问题**：年级限定是直接报名的附加前置条件，不是新的结果状态。
- **备选**：① 在 RegistrationService.register() 里加 if policy_type == grade_direct；② 新建一个完全独立的 GradeDirectPolicy 复制直接报名逻辑；③ 规则 + 组合。
- **选择**：③。规则只回答“放行与否”，组合策略保留原有策略产出状态的能力（occupies_capacity_on_submit 等语义不变）。
- **代价**：多两个类与一层间接；收益是服务零改动、规则可叠加（专业/学院限定只需再加一条 Rule）、边界可独立测试。
- **证据**：git diff 中 services.py 为空；CR1-05 证明原有公共约束与 direct 行为均未改变。

## 决策八（v2 / CR-02）：邮件用“并列观察者 + 端口”，不改造站内通知

- **问题**：邮件是第二通知渠道，失败语义与站内消息不同（不能回滚报名）。
- **备选**：① 在 InAppNotificationObserver 内追加发信；② 在服务里直接发信；③ 新增独立观察者 + EmailSender 端口。
- **选择**：③。两个观察者互不连坐，总线逐条 try 并记录 ailures；发信实现可替换为 SMTP。
- **幂等**：复用 vent_key，(recipient, event_key) 唯一约束 + 发送前查重，双保险。
- **失败处理顺序**：捕获 EmailSendFailed → 写 EmailRecord(status=发送失败, error) → commit → 抛出供总线留痕，因此“记录一定有、报名不回滚”。
- **代价**：多一张表与一个页面；收益是可审计、可替换、可演示故障路径（CAMPUS_EVENT_EMAIL_FAIL_TIMES）。
