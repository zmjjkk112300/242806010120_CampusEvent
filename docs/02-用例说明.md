## 2.2 UC-03 报名活动（核心用例）

| 项 | 内容 |
|---|---|
| 参与者 | 学生 |
| 前置条件 | 学生已登录；活动存在且未开始 |
| 触发 | 学生在活动详情页点击“立即报名” |
| 后置条件（成功） | 生成一条报名记录（直接报名=已通过，审核型=待审核）；生成一条站内消息；统计随之变化 |
| 后置条件（失败） | 不产生任何报名记录，页面显示中文失败原因 |

**基本流**

1. 系统读取活动与当前学生信息。
2. 校验活动存在、开始时间晚于当前时间。
3. 校验该学生在此活动上没有“待审核/已通过”的有效报名。
4. 依据活动的 `policy_type` 从策略注册表取出策略实现。
5. 若策略声明“提交即占名额”（直接报名），校验已通过人数 < 容量。
6. 策略返回初始状态与事件类型。
7. 写入报名记录并提交事务。
8. 事务提交后发布领域事件，通知观察者写入站内消息。
9. 页面提示“报名成功”或“待审核”。

**异常流**

| 分支 | 条件 | 系统响应 |
|---|---|---|
| A1 | 活动不存在 | 提示“活动不存在或已被删除” |
| A2 | 活动已开始 | 提示“活动已开始，无法报名或取消报名” |
| A3 | 已存在有效报名 | 提示“你已报名该活动，请勿重复报名”，不新增记录 |
| A4 | 直接报名且名额已满 | 提示“名额已满，无法完成该操作”，不新增记录 |
| A5 | 审核型且名额已满 | 允许提交（待审核不占名额），批准阶段再次校验 |
| A6 | 通知写入失败 | 报名仍成功；失败写入日志与事件总线 `failures`，不回滚报名 |

## 2.3 UC-07 审核报名（核心用例）

| 项 | 内容 |
|---|---|
| 参与者 | 管理员 |
| 前置条件 | 存在“待审核”报名 |
| 触发 | 管理员在审核页点击“批准”或“拒绝” |
| 后置条件 | 报名状态变为“已通过”或“已拒绝”，并生成对应站内消息 |

**基本流（批准）**

1. 系统读取报名记录，校验状态为“待审核”。
2. 读取活动容量，统计当前“已通过”人数。
3. 若已通过人数 ≥ 容量 → 拒绝批准，提示“名额已满，无法批准该报名”，状态保持“待审核”。
4. 否则将状态更新为“已通过”，提交事务。
5. 提交后发布 `registration.approved` 事件，写入站内消息。

**异常流**

| 分支 | 条件 | 响应 |
|---|---|---|
| B1 | 报名已是“已通过/已拒绝/已取消” | 提示“只有待审核的报名可以批准/拒绝” |
| B2 | 名额已满 | 批准失败，人数不超上限 |
| B3 | 报名记录不存在 | 提示“报名记录不存在” |

## 2.4 UC-04 取消报名

前置：报名状态为“待审核”或“已通过”，且活动未开始。
基本流：校验操作人为报名本人 → 状态置“已取消” → 提交 → 发布 `registration.cancelled` 事件并通知。
异常流：他人记录（提示“只能操作自己的报名记录”）；活动已开始（提示“活动已开始…”）；状态不可取消。
说明：取消后原记录保留，学生可再次申请（历史可追溯）。

## 2.5 UC-06 管理活动

| 分支 | 行为 |
|---|---|
| 新增 | 校验名称非空（≤120 字）、时间为合法日期时间、容量 1—1000 正整数、报名方式合法；通过后写库 |
| 编辑 | 同新增校验；更新后列表与详情一致 |
| 删除 | 若活动已有任意报名记录 → 拒绝删除并提示；否则物理删除 |

## 2.6 UC-08 查看统计

活动详情页与管理页展示：容量、已通过数、待审核数、剩余名额（剩余 = max(容量 − 已通过, 0)）。
待审核不计入已通过，因此不会提前占用名额。
